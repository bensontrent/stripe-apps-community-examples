# AGENTS.md — notes for whoever picks this up next

Context: this repo is the quickstart example for the **Stripe Apps Community meetup**: a Stripe App (UI extension) plus a Next.js backend. Since 2026-09-20 the backend is published as a **Stripe Projects build template** and the Stripe App is meant to live in its own repo, referenced here as a submodule.

## Repo layout

- `stripe-app-nextjs-backend/` — Next.js 16 backend **and the Stripe Projects template**: Better Auth (email/password + sessions) over a direct `pg` connection, supabase-js for app data, Supabase Postgres, Stripe webhook handler, signed-request routes + Dashboard login handshake. Own docs: `README.md`, `QUICKSTART.md`, `ARCHITECTURE.md`, `AUTHENTICATION.md`, `DEPLOYMENT_QUICK_START.md`, and a consumer-facing `AGENTS.md` that ships with the template. Manifest: `projects-template.yaml`.
- `stripe-app/` — Stripe App UI extension (`@stripe/ui-extension-sdk` 9.3.0, React 18). App id `com.productivity.community-example`, display name "Community Example". Two views: `stripe.dashboard.fullpage` (`views/FullPage.tsx`, routed with `@stripe/ui-extension-sdk/navigation`) and `stripe.dashboard.drawer.default` (`views/App.tsx`, lists the examples and opens each in the full-page app). Run with `stripe apps start`. Self-contained (own README, LICENSE, .gitignore) so it can be split into its own repo.
- Root `package.json` — no npm workspaces (deliberate, see below). `postinstall` runs `npm install --prefix` in each subfolder. `npm run dev` uses `concurrently` to run both.

## Stripe Projects conversion (2026-09-20)

What "publishing as a Stripe Project" means: a **build template** = a public GitHub repo (or subdirectory) + a YAML manifest PR'd into [stripe/projects-template-registry](https://github.com/stripe/projects-template-registry). `stripe projects build --template <id>` copies the files at a pinned commit, runs `install_command`, provisions the `services`, and prints `next_steps`. Docs: <https://docs.stripe.com/projects/templates>. Stripe's own templates: <https://github.com/stripe/projects-templates> (MIT — `scripts/deploy-vercel.mjs` is adapted from `nextjs_saas_amber-fox`).

Decisions:

- **Template = the `stripe-app-nextjs-backend/` subdirectory** of this repo (`repo:` in the manifest is a `/tree/main/stripe-app-nextjs-backend` URL). The Stripe App is *not* part of the template; the manifest's next steps tell users to `git clone` it.
- **Services:** the default manifest (`projects-template.yaml`, variant `vercel`) provisions **only `vercel/project`**. Maintainer decision 2026-09-20: Stripe Projects' Supabase connector can't select an existing project or a schema (`existing_resource_linking: unsupported` for both Supabase and Vercel), and this backend's own Supabase connection (existing project, session pooler, `SUPABASE_SCHEMA`) must stay the primary path. Provisioning Supabase through Projects is kept as a *valid option*: a choice inside `npm run setup` (runs `stripe projects add supabase/project`), the plain CLI command, and a second, non-default manifest variant `projects-template.supabase-vercel.yaml` (variant `supabase-vercel`).
- **Env var names.** Supabase's provider writes `SUPABASE_PROJECT_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_PROJECT_REF`, `SUPABASE_DB_URL`, `SUPABASE_POOLER_URL`, `SUPABASE_DB_PASS` (names taken from PostHog's and Mixpanel's published Supabase templates; **whether a `SUPABASE_SECRET_KEY` is emitted is unverified** — no real provisioning was run). Vercel writes `VERCEL_TOKEN`, `VERCEL_PROJECT_ID`, `VERCEL_TEAM_ID`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_URL`. Rather than rename everything, `src/lib/env.ts` (runtime) and `scripts/env.mjs` (CLI scripts) map provider names onto the classic names the code reads (`DATABASE_URL` ← `SUPABASE_POOLER_URL`|`SUPABASE_DB_URL`, `NEXT_PUBLIC_SUPABASE_URL` ← `SUPABASE_PROJECT_URL`, `SUPABASE_SERVICE_ROLE_KEY` ← `SUPABASE_SECRET_KEY`, anon ← `SUPABASE_PUBLISHABLE_KEY`). Classic names win; placeholders from `.env.example` count as unset. **Keep the two tables in sync.** Verify the secret-key question on the first real `stripe projects add supabase/project`; if it isn't emitted, the checklist/setup already tell users to store it with `stripe projects variables set … --env-key SUPABASE_SECRET_KEY`.
- **Two env files.** `.env` is owned by `stripe projects env --pull` (provider creds). `.env.local` holds everything else and wins (Next.js precedence). Both gitignored; `.projects/cache` and `.projects/vault` gitignored, `state.json`/`state.local.json` are meant to be committed *by template consumers* (this repo itself is not `stripe projects init`ed).
- **`delete_me_after_setup/` is gone.** Replaced by `scripts/setup.mjs` — append-only, idempotent, interactive when stdin is a TTY (`--non-interactive` / CI otherwise). The old wizard's Supabase questions live on here (existing project → paste session-pooler string + API keys; new free project via database.new; dedicated schema), plus a new choice to provision via Stripe Projects. Then: random secrets, Stripe test key from `stripe config --list` (amber-fox trick; accepts `sk_test_`/`rk_test_`, falls back to asking), tables via `ensureTables()` exported from `scripts/db-setup.mjs` (which only runs `main()` when invoked directly). Provisioning happens *after* `install_command`, so setup must be a `next_steps` command, not part of install. `SetupChecklist.tsx` no longer depends on a folder existing: dev-only, hides itself when every item is green, and labels values with the provider variable they came from when Projects supplied them.
- **Deploy:** `npm run deploy` (`scripts/deploy-vercel.mjs`) — REST-only, no Vercel CLI: syncs `.env`+`.env.local` (minus a denylist, plus resolved classic names, `BETTER_AUTH_URL` rewritten to `https://<VERCEL_PROJECT_URL>`) to the project's production env, uploads files (skipping `.projects/`, `.env*`, `.next`, `node_modules`), creates a deployment. Untested against a real Vercel project.
- **Names fixed while here:** docs/hints referred to `STRIPE_APP_SECRET` and `STRIPE_APP_SECRET_KEY_*`; the code reads `STRIPE_APP_SIGNING_SECRET` and `STRIPE_SECRET_KEY_*`. `env.d.ts`, `backend.ts` hints and the docs now match the code. `CRON_SECRET` is *not* set automatically by Vercel — Vercel sends it as a bearer token when you set it (docs corrected).
- **Submitted to the registry 2026-09-21.** `stripe-app/` is its own repo + submodule; both manifests are pinned to `1ce2e22` (the in-repo files mirror the registry copies exactly) and submitted as [stripe/projects-template-registry#31](https://github.com/stripe/projects-template-registry/pull/31) — files `stripe_app_backend/vercel.yaml` and `stripe_app_backend/supabase-vercel.yaml`, from fork branch `bensontrent/projects-template-registry:add-stripe-app-backend`. The release procedure for later versions is in the header of `projects-template.yaml` (`ref` trails the template change by one commit, then a registry PR copies both files). Still open: sign the CLA on the PR; once merged, run one real `stripe projects build --template bensontrent/stripe-app-nextjs-backend` per variant (projects plugin 0.41.0 has no `--template-manifest` flag, and a build creates a real Stripe project + Vercel project, the second variant a Supabase project too) and confirm whether `SUPABASE_SECRET_KEY` is emitted. `guided.category: stripe_app` is not a first-class category, so it lists under "Something else".
- **Stripe clients are lazy (2026-09-21).** `src/lib/stripe.ts` creates each `Stripe` client on first `getStripeClient()` call and throws an error naming the missing `STRIPE_SECRET_KEY_*` / `STRIPE_WEBHOOK_SECRET_*` variable; nothing is validated at import. Before, `next build` failed on `/api/stripe/webhook` unless all three app keys were set — but a fresh template checkout only has the test key after `npm run setup`. A pristine copy of the tracked files must keep building and serving with **no env vars at all** (verified 2026-09-21: build, `GET /` 200, webhook 500 with a clear log); keep that property.

## Decisions made earlier (and why)

- **No npm workspaces.** The Stripe CLI builds the app from `stripe-app/` and expects its dependencies locally; hoisting to a root `node_modules` is a risk not worth taking. `--prefix` scripts are boring and reliable. With the submodule, `npm install` at root needs `git submodule update --init` first.
- Root README stays high-level and links into the backend's docs rather than duplicating them.

## Database workflow (Drizzle removed 2026-07-07)

- Data access is plain **supabase-js** (`src/lib/supabase.ts`, secret/service-role key, lazily created — server-side only) and Better Auth connects directly over `DATABASE_URL` with a `pg` Pool.
- **Migrations since 2026-09-30** (maintainer decision: the project is no longer greenfield, other people run databases built from it). The schema = `stripe-app-nextjs-backend/setup.sql` (the **baseline**, idempotent, frozen) + every file in `stripe-app-nextjs-backend/migrations/` in filename order. `npm run setup` / `npm run db:setup` (`scripts/db-setup.mjs` `ensureTables()`, returns `{ state, migrations }`) applies the baseline, then each `YYYYMMDDHHMMSS_description.sql` not yet listed in the `applied_migrations` table (created by `setup.sql`), one transaction per file; a misnamed `.sql` file is an error. `--print` emits the SQL a fresh database needs (baseline + all migrations + their tracking rows).
- **Rule: a schema change = a new file in `migrations/`** (conventions in `migrations/README.md`: unqualified names so `SUPABASE_SCHEMA` works, RLS on new tables, no `BEGIN`/`COMMIT`, never edit an applied file). Don't edit `setup.sql`; its "Upgrades" section is closed. This supersedes the "edit the CREATE + add an Upgrades ALTER" rule that older notes below still mention. Location chosen over `supabase/migrations/` on purpose: that folder implies the Supabase CLI, which keeps its own tracking table and knows nothing about `SUPABASE_SCHEMA`; the filename format is the Supabase one, so the files can move there later.
- The folder shipped with only its README; the first migration (`20261001004106_stripe_accounts_email.sql`) came from the webhook work the same day, see "Webhooks" below. Verified 2026-09-30 against `xcqewnpyuzknxjnximju`/`example` with throwaway files (since removed, along with their rows): applied once into the `example` schema, skipped on re-run, a failing file rolled back completely with exit code 1.
- RLS is enabled on every table with no policies: Supabase's auto REST API exposes `public`, so the anon/publishable key must be locked out; the backend's secret key bypasses RLS.
- **Schema structure (redesigned 2026-07-20; 8 tables):** Better Auth models (`users`, `sessions`, `auth_accounts`, `verifications` — `users` also carries app-owned `settings` jsonb and `stripe_customer_id_live`/`_test`); merchant side (`stripe_accounts` keyed by `acct_` id with `settings` + `live_installation_id`/`test_installation_id`; `memberships` user ↔ account with `role` owner/admin/member and per-account `settings`); `stripe_app_sessions` (dashboard login link); publisher side (`subscriptions` keyed by `sub_` id). Conventions: Stripe ids are natural primary keys; `livemode` only where Stripe itself splits data; `timestamptz` everywhere; every FK column indexed.
- **Better Auth mapping is non-default:** `src/lib/auth.ts` maps `user`/`session`/`account`/`verification` onto `users`/`sessions`/`auth_accounts`/`verifications` via `modelName`/`fields` (snake_case) with `uuid` ids. `auth_accounts` is deliberately not `accounts` to avoid confusion with Stripe accounts. When changing the four auth tables, keep the columns Better Auth expects and update the `fields` maps.
- **Custom schema support (`SUPABASE_SCHEMA`):** threads through `scripts/db-setup.mjs` (creates the schema, sets `search_path`, grants API roles), `src/lib/supabase.ts` (validated `dbSchema`, `db: { schema }`), `src/lib/auth.ts` (`search_path` per pool connection — needs the session pooler), and the checklist/setup. The one step SQL can't automate: add the schema to "Exposed schemas" in the Supabase dashboard — the checklist probes PostgREST and flags it.

## Authentication framework (added 2026-07-05)

`stripe-app-nextjs-backend/src/proxy.ts` is a multi-flavor auth router (Next.js 16 "proxy" = the old middleware). Full docs in `AUTHENTICATION.md`. The pieces:

- `src/lib/proxy-auth.ts` — verification helpers: Stripe App signature (`stripe-signature` header vs `STRIPE_APP_SIGNING_SECRET`), bearer keys (`BEARER_TOKEN_KEYS`/`CRON_SECRET`), dev-only key (`DEV_API_KEY`, NODE_ENV=development only), user API keys (stubbed TODO — future DB lookup), CORS helpers.
- `src/lib/url-token.ts` — short-lived JWT-in-URL tokens (`jose`, HS256, `URL_TOKEN_SECRET`), verified at the route level; path + account bound.
- Example routes, one per flavor: `/api/stripe-app/me` (signature), `/api/stripe-app/token` (mints URL tokens), `/api/public/download` (JWT-in-URL, public in proxy), `/api/cron` (bearer-only).
- The proxy strips `x-auth-type`/`x-stripe-verified` from incoming requests and sets them after verification — routes trust them; never remove that stripping.
- `stripe-app/src/api/backend.ts` — signed-fetch client (`fetchStripeSignature`) with example calls, pointing at `http://localhost:3006` in dev; `stripe-app.json` CSP `connect-src` lists a placeholder https URL users must replace before publishing. The backend dev server runs on port **3006**.

## Stripe App user login flow (added 2026-07-20)

- **Handshake:** the app mints a `state` UUID, opens `{backend}/stripe?state=…` in a browser tab, and polls `GET /api/stripe-app/verify?state=…` (signed). The `/stripe` page (session auth) POSTs the state to `/api/stripe-app/session`; verify claims it, writes `stripe_app_sessions` (+ `memberships`, first = owner), and consumes the state (one-shot). `GET /api/stripe-app/userinfo` resolves the signed dashboard identity thereafter; logout = `DELETE /api/stripe-app/session` + the `/stripe-logout` page. Full docs: `AUTHENTICATION.md` ("The Stripe App user login flow").
- **Tables:** `stripe_app_sessions` (PK stripe_account_id + stripe_user_id). Handshake states reuse Better Auth's `verifications` table (identifier `stripe-app-login:<state>`, 15-min TTL).
- **Backend pieces:** `src/lib/stripe-app-session.ts`, routes `/api/stripe-app/{session,verify,userinfo}`, `sendResetPassword` in `src/lib/auth.ts` (since 2026-09-29 emails the reset link through Postmark via `src/lib/email.ts` — plain `fetch`, no SDK — when `POSTMARK_SERVER_API_TOKEN` + `POSTMARK_FROM_EMAIL` are set; otherwise, or on a send failure under `next dev`, prints it to the terminal, which keeps the no-env build/serve property), and a `(login)` route group sharing one card layout + `components.tsx` + `redirect.ts`.
- **App pieces:** `stripe-app/src/components/Login.tsx` (state machine, 5s polling), helpers in `src/api/backend.ts`, wired as section 3 of `src/components/BackendDemo.tsx`, rendered by `pages/ExampleDetail/AuthenticationExample.tsx` at `/examples/authentication`.
- **Verified 2026-07-20** end-to-end against Supabase project `xcqewnpyuzknxjnximju`, schema `example`.
- **Machine quirk:** this PC had stale *user-scope* Windows env vars (`NEXT_PUBLIC_SUPABASE_URL`, …) overriding `.env.local` (process env beats env files in Next.js). Deleted 2026-08-04; `.claude/launch.json` (gitignored) still clears them defensively.

- SDK upgraded 9.2.0-alpha.16 → **9.3.0** (full-page apps need 9.2.1+). The 9.3.0 package ships ES modules, so `jest.config.ts` now runs `ts-jest` over `node_modules/@stripe/ui-extension-sdk` and `@remote-ui` (`transformIgnorePatterns`); without that every test fails with "Cannot use import statement outside a module".
- **Route config is `src/routes.tsx`** (`createRoutes` + `RouteRegister` augmentation → typed `createAppRoute`/`navigateToAppRoute`). Routes: `home` `/:tabId?`, `example` `/examples/:slug`, `customer` `/customers/:customerId`, `invoice` `/customers/:customerId/invoices/:invoiceId`, `legacyDemo` `/demo/:slug` (Redirect). The drawer also deep-links `/customers/:id` from `environment.objectContext` on customer pages; `pages/CustomerDetail` hands unknown ids to the native Dashboard page with a `customerDetails` route descriptor.
- The example list is data: `src/examples/catalog.ts` holds the two examples the app links to (`authentication` → `components/BackendDemo.tsx`, `app-settings` → `components/SettingsDemo.tsx`); slug = URL segment, so renaming one means adding a Redirect. Maintainer decision (2026-09-21): the drawer `views/App.tsx` is a *list of the examples* (from the catalogue) that opens each one at `/examples/<slug>` in the full-page app; demos render only in the full-page routes. ## App settings (added 2026-09-21)

Roadmap item "App settings (user, account-wide and test mode settings)" — modeled on Parcelcraft's `SettingsController` + `patchSettings`, minus the parts we don't want people to copy (Redis cache, read-merge-write, unvalidated keys).

- **Model:** `src/types/settings.ts` — **identical copies** in `stripe-app-nextjs-backend/` and `stripe-app/` (separate packages, deliberately no shared package; keep in sync by copying). Explicit `AccountSettings` / `UserSettings` types, `DEFAULT_SETTINGS`, and `SETTING_DEFINITIONS` (scope + optional `options`) typed `Record<SettingKey, …>` so all three must agree.
- **Identity = the signature, not a login (maintainer correction 2026-09-21):** settings are owned by the ids the proxy-verified signature vouches for — `stripe-account-id` (acct_) and `stripe-user-id` (usr_, normalized to '' for Connect/platform callers like `stripe_app_sessions`). No Better Auth login involved; that login stays an optional, separate step (e.g. paying for the app). Consequently there is **no role gate** on account-scoped writes (every Dashboard user of the account may write; docs say how to add one via `memberships.role`).
- **Schema (maintainer decision 2026-09-21: a `livemode` column, not nested buckets):** two tables, `account_settings` PK `(stripe_account_id, livemode)` and `user_settings` PK `(stripe_account_id, stripe_user_id, livemode)`, each with a `settings` jsonb. Test and live are **different rows**; the same routes serve both, selected by the (unsigned) `stripe-mode` header. The old `settings` jsonb columns on `users`, `stripe_accounts` and `memberships` were **dropped** (and `accountSettings`/`userSettings` removed from `POST /api/protected/stripe-app`).
- **Backend:** `src/lib/settings.ts` (`SettingsOwner`, `loadSettings`, `patchStoredSettings`), route `src/app/api/stripe-app/settings/route.ts` (GET + PATCH, signature auth only; `validatePatch` → 400). PATCH answers with the full GET payload.
- **Merge is in SQL:** `setup.sql` has `settings_merge(current, patch)` (patch wins, null deletes) and the upserts `patch_user_settings(text, text, boolean, jsonb)` / `patch_account_settings(text, boolean, jsonb)` (create the `stripe_accounts` row and the mode row on first save); called via `supabase.rpc()` (PostgREST resolves them in the configured schema — verified on the `example` schema 2026-09-21). Applied to `xcqewnpyuzknxjnximju`/`example` as migrations `example_app_settings_functions`, `example_app_settings_tables_livemode`, `example_app_settings_stripe_ids`.
- **`setup.sql` is idempotent since 2026-09-21** (maintainer request): `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`, plus an "Upgrades" section at the end (`DROP COLUMN IF EXISTS` for the old settings columns, `DROP FUNCTION IF EXISTS` for superseded signatures). `ensureTables()` now always applies the file (returns `'created'` | `'updated'`), so `npm run db:setup` is the upgrade path. **Rule change:** a schema change = edit the CREATE statement *and* add an idempotent ALTER to the Upgrades section — `CREATE TABLE IF NOT EXISTS` never alters an existing table.
- **App:** `src/hooks/useSettings.tsx` — `SettingsProvider` (one fetch per view, React-context state, optimistic updates, sequence-numbered so a late response can't undo a newer save, reload on error) + `useSettings()`; typed `updateUserSettings` / `updateAccountSettings`. Sections in `src/components/SettingsDemo.tsx` (same drawer/full-page split as `BackendDemo.tsx`), used by `src/pages/ExampleDetail/SettingsExample.tsx` (`/examples/app-settings`) and the drawer `src/views/App.tsx`. Client calls in `src/api/backend.ts` (`getSettings`, `patchSettings`). Tests: `src/types/settings.test.ts`, `src/components/SettingsDemo.test.tsx`. **Dashboard layout rule (cost an hour):** `PageModule` must be a direct child of `DetailPage`/`OverviewPage` — wrapping modules in a `Box` (e.g. via `<Login>` children) throws "Invalid usage of PageModule" in the host and the tab appears frozen for ~20 s before the error shows.
- **Docs:** `src/content/docs/app-settings.md` (order 4; writing-docs moved to 5).

## Paywall, trials and billing (added 2026-09-29)

Roadmap items "App paywall", "App monetization and user billing dashboard" and "App trial strategies" — modeled on Parcelcraft's `PayWall.tsx` / `pay-wall-gate.ts` / `PlanDetails.tsx`, with the decision moved to the backend and the custom plan picker replaced by Stripe Checkout + the customer portal.

- **Model:** `src/types/paywall.ts` — **identical copies** in both packages, same arrangement as `settings.ts`. `resolvePaywall()` is the whole policy (order: test mode → subscribed → past due → trial not started → expired → limit reached → trialing). The backend decides and sends `PaywallStatus` (`access`, `reason`, `view`); the app only renders `view`. The copy in the app exists for the demo's preview section and the unit tests.
- **Maintainer requirements:** trial is **per Stripe account**; **test mode is excluded** (no paywall). `TRIAL_COUNT_LIMIT` (default 25) and `TRIAL_DAYS_LIMIT` (default 30) are backend env vars, `0` switches a limit off (sent to the app as `null`). Limits are policy applied at read time, not stored, so changing one affects running trials.
- **Decisions made here (not dictated):** the trial starts when someone accepts the intro view, not at install (no install webhook needed; row is never deleted, so reinstalling buys no second trial). `PAYWALL_ENFORCE_IN_TEST_MODE=true` exists only so the flow can be rehearsed locally in test mode. The trial is per mode (it lives on the per-mode `account_settings` row) so rehearsing doesn't consume the live trial. A `past_due` subscription blocks even with trial allowance left.
- **Coverage rule:** subscriptions belong to Better Auth users; an account is covered when **any member** (`memberships`, created by the Dashboard login handshake) has an `active`/`trialing` subscription whose `livemode` matches the app's mode. One plan covers every account its owner works in (Parcelcraft's model). Per-account selling is documented as a variation, not implemented.
- **Backend:** `src/lib/paywall.ts` (config, facts, `loadPaywallStatus`, `startTrial`, `recordFeatureUse` = the gate, `refreshPaywallStatus`, dev-only `resetTrial`), `src/lib/signed-request.ts` (`getSignedIdentity`; the settings route still has its own inline copy), routes `/api/stripe-app/paywall{,/trial,/usage,/refresh}`. `/usage` is the example gated route and answers **402** with the status in the body. `DELETE /paywall/trial` is 404 unless `NODE_ENV=development`.
- **SQL (maintainer decision 2026-09-29: no new table — "I do not like having more tables than needed"):** the trial is two columns on `account_settings`, `trial_started_at` (NULL = not started) and `trial_usage_count`. An `account_trials` table existed for a few hours, uncommitted, and was dropped. They are columns, not keys in the `settings` jsonb, because the app can PATCH that document. Their `ADD COLUMN IF NOT EXISTS` sits in the Paywall section of `setup.sql`, not in Upgrades: `LANGUAGE sql` functions are validated at creation, so the columns must exist before the functions. `resetTrial` clears the two columns and leaves `settings` alone. `start_account_trial()` (idempotent, returns the `account_settings` row) + `record_trial_usage()` (check and increment in one UPDATE; returns NULL when nothing was counted), `subscriptions.price_lookup_key` (CREATE + Upgrades `ADD COLUMN IF NOT EXISTS`). ## Webhooks: app + billing, install emails (added 2026-09-30)

Modeled on Parcelcraft's `dashboard-parcelcraft/pages/api/app_webhook.ts` + `webhook.ts` and the Express controller `parcelcraft-backend/src/controllers/webhooks/stripe.ts` (install/uninstall).

- **Two routes, Pages Router (maintainer request):** `src/pages/api/webhooks/app.ts` (`/api/webhooks/app?mode=live|test&type=connected|managed_sandbox|account`) and `src/pages/api/webhooks/billing.ts` (`/api/webhooks/billing?mode=live|test`), `bodyParser: false`, raw body via `readRawBody()` in `src/lib/webhooks.ts`, verified with the static `Stripe.webhooks.constructEvent` (needs no API key). They replace the App Router route `src/app/api/stripe/webhook/route.ts` (deleted; `PUBLIC_ROUTES` now lists `/api/webhooks`). No `micro` dependency.
- **The App Router was not actually broken:** before it was deleted, the old route (`await req.text()`) accepted a locally signed event and rejected a tampered one. The maintainer asked for the Pages Router believing raw bodies were unsolved in the App Router; that finding was reported back. **Cost of having `src/pages` at all:** Next then types `useSearchParams()` / `usePathname()` as nullable, which broke `next build` in 5 App Router files — fixed with `?.`/`??` guards (`(login)/confirm/page.tsx`, `(login)/redirect.ts`, `(login)/stripe/page.tsx`, `(site)/billing/page.tsx`, `SiteHeader.tsx`); new uses of those hooks need the same. Moving the two routes back to `src/app/api/webhooks/{app,billing}/route.ts` keeps the URLs and removes that cost — the handlers are thin and the logic is in `src/lib`.
- **Install / uninstall:** `src/lib/app-installs.ts` handles `account.application.authorized` / `.deauthorized` (the events the maintainer asked for; Stripe also sends `apps.install.*`, which the pinned SDK/API version `2026-03-25.dahlia` does not type — documented as an alternative, don't handle both). Install: `stripe.accounts.retrieve(event.account)` → name + contact email into `stripe_accounts`, then one conditional UPDATE writes the event id into `live_installation_id` / `test_installation_id` (by `event.livemode`) only if it was NULL. Uninstall: conditional UPDATE back to NULL, delete the account's `stripe_app_sessions`, never delete the row (trial + settings hang off it), never cancel a subscription. Emails are per account, not per mode (welcome when the first mode installs, goodbye when the last one goes). Events without `event.account` (the own-account copy) are ignored.
- **Mode comes from `event.livemode`, not the endpoint:** Stripe sends test-mode events of an account installed in both modes to the live Connect endpoint too (docs.stripe.com/stripe-apps/build-backend, "Event behavior depends on install mode"). The query string only selects the signing secret.
- **Emails:** `src/lib/email-templates.ts` — `welcomeEmail()` / `goodbyeEmail()` return `{ subject, text, html }` for `sendEmail()`; `APP_NAME` constant; the welcome quotes the trial from `paywallConfig()`. Skipped (and reported in the webhook's `result`) when Postmark isn't configured, so the no-env build/serve property holds.
- **Schema:** the first real migration, `migrations/20261001004106_stripe_accounts_email.sql` (`stripe_accounts.email`), applied to `xcqewnpyuzknxjnximju`/`example` with `npm run db:setup`. New optional env var `STRIPE_APP_ACCOUNT_ID` (own account id for `type=account` events).
- **Verified 2026-09-30** on `next build` + `next start -p 3007` with locally signed events (Postmark blanked and the live key replaced by the test key for that process, because this machine's `.env.local` has a real Postmark token and live key): 405 / 400 missing signature / 400 tampered / 500 unset secret / 200 unhandled; install → redelivery no-op → second mode no second welcome → partial uninstall → full uninstall (app sessions 1 → 0, row kept) → redelivery no-op; 7 concurrent installs → exactly one welcome; billing: unknown customer skipped. Both emails rendered and eyeballed. **Not verified:** a real install/uninstall event from Stripe (so `accounts.retrieve` returning an email for an installed account is taken from Parcelcraft's production code, not observed here), an actual Postmark delivery of the two templates, the `type=account` and managed-sandbox endpoints with their own secrets (this machine's test/live/sandbox secrets are all the same `stripe listen` value), `syncSubscription` from a real billing event, and the `stripe listen --forward-connect-to … --forward-to …` command in the docs (flags checked against CLI 1.45.1 `--help` only).
